## 1. What it is

BreakWall is a knowledge graph over a pile of markdown: project documentation and the artifacts produced per work item during application development (specs, designs, test plans, decision records, retros). Agents and humans query it to answer "what do we already know about X, and where is it written".

It is a sibling of Undertow, not a fork. They share infrastructure ideas (Neo4j, embeddings, graph algorithms) and almost nothing else, because the data has a different nature.

## 2. Why it is not Undertow

Undertow remembers a conversation. BreakWall indexes a library. That one difference flips most design choices.

| Axis | Undertow (episodic memory) | BreakWall (reference corpus) |
|---|---|---|
| Source of truth | The graph itself | The files. The graph is a derived, rebuildable index |
| Change | Constant, driven by sessions | Grows only on purpose, rarely edited, never driven by a chat |
| Write path | Hooks ingest tool events and turns, LLM writes "neurons" | None from agents. Read-only to them. Writes only by re-indexing the files |
| Unit | LLM-authored neuron (name, one-line flash, body) | A verbatim section of the document, with its heading path |
| Ranking over time | Decay, pursuit/dismissal reinforcement, habituation | None. Ranking must be stable and reproducible for the same query |
| Delivery | Ambient: a flash injected on every prompt | On demand: tools the agent calls, with citations |
| Trust | A paraphrase is fine, memory is fuzzy | Quote and cite. A wrong paraphrase of a spec is a defect |
| Gatekeeping | Keeper decides whose sessions deserve memory | Not needed. Nothing is ingested from sessions |
| Failure mode | Poisoned or stale memory | Stale or contradicted document, dangling link, missing coverage |

Consequences: no decay, no reinforcement, no Keeper, no Dreamer/Wonder/Gobble equivalents. What replaces them is deterministic parsing, provenance, and an evaluation harness.

## 3. Principles

1. Files are canonical. Delete the graph, re-run the indexer, get the same graph.
2. Provenance on everything: file path, heading path, line range, content hash, git commit.
3. Deterministic edges are separate from inferred edges. Never mix them in one relationship type. Inferred edges carry a method and a confidence.
4. Retrieve, quote, cite. Return the original text plus where it lives. Summaries are optional and labelled.
5. Stable answers. Same query, same corpus version, same ranking.
6. Read-only to agents. The only way knowledge enters is a human adding a file.
7. Simplest thing first. Deterministic structure first; vector search is in from M2 alongside lexical search (RouterBox's decision); LLM extraction last.

## 4. Data model

Deterministic layer (from parsing only, no LLM):

- Corpus: a named root folder (supports several corpora in one install).
- Document: path, title, frontmatter, content hash, git commit, status (current, superseded).
- Section: a heading and its body, with parent/child heading tree, ordinal, line range, text, hash. This is the retrieval unit.
- Block (optional, later): code fences, tables, checklists, as typed children of a section.
- WorkItem: id parsed from path or frontmatter (for example folder name or a `work-item:` key). Phase: spec, design, build, test, retro, decision.
- Tag: from frontmatter and inline tags.

Deterministic relationships: CONTAINS (corpus>document>section>block), NEXT (reading order), LINKS_TO (relative link or wikilink, resolved to document or section), BELONGS_TO (document>work item), TAGGED, SUPERSEDES / SUPERSEDED_BY (from frontmatter or an explicit "supersedes:" line), MENTIONS_ID (references to a work item id or file path found in text).

Inferred layer (optional, each edge records method, model, score, run id):

- SIMILAR_TO between sections by embedding distance above a threshold.
- Entity and concept nodes extracted by an LLM, canonicalised against a glossary, linked by DEFINES / USES / DEPENDS_ON.
- Community (topic cluster) and centrality, computed at build time with Neo4j GDS, used for browsing and ranking tie-breaks, not for decay.

## 5. Ingestion

1. Walk the corpus (respect an ignore file). Hash every file.
2. Diff against the index by hash. Only changed or new files are reprocessed. Renames are detected by hash. Deletions leave a tombstone.
3. Parse with a real markdown AST (mdast), not regex. Extract the heading tree, links, frontmatter, tags.
4. Resolve links. Report dangling links and orphans (the graph doubles as a linter).
5. Chunk by section. Very long sections split by paragraph with an overlap marker, keeping the parent heading path as context.
6. Embed each section (cache by content hash, so unchanged text is never re-embedded).
7. Optionally run inferred-edge passes as separate, re-runnable jobs.
8. Write in one transaction per document so a failed run never leaves a half-indexed file.

Triggers: manual command, file watcher, and a git hook or CI step. Because the corpus grows intentionally, a manual or per-commit run is enough to start.

## 6. Retrieval and delivery

Hybrid search: lexical (BM25 or full-text) plus vector similarity, fused with reciprocal rank fusion, then optional graph expansion (parent section, linked sections, same work item).

Delivery is pull, not push. A small tool surface (MCP server and CLI, same core):

- `search(query, filters)`: ranked sections with path, heading path, quoted text, score, why-matched.
- `get(path, heading)`: exact section text.
- `outline(path)`: heading tree of a document.
- `neighbors(section)`: what links to it and what it links to.
- `work_item(id)`: everything for a work item, grouped by phase.
- `trace(from, to)`: shortest explanation path between two concepts or documents.
- `history(topic)`: supersession chain, newest first.
- `coverage` and `lint`: dangling links, orphans, documents never linked, duplicate sections.

Every result carries a citation and the corpus commit it came from. A token budget parameter caps the returned text. A UserPromptSubmit hook option (decided) injects a few top citations on each prompt, RAG style, under a strict token budget and a relevance threshold so it stays silent when nothing matches. It is read-only, off unless enabled for a project, and uses the same `search` core as the MCP tools. Hook safety rules (decided 2026-10-27): a hard timeout of about one second, and a silent exit if BreakWall is down, so a stopped container can never slow a prompt; skip very short prompts; cap the injected tokens; and share one context budget with Undertow's flashes, skipping anything Undertow already surfaced in the same prompt.

## 7. Staleness without decay

Documents do not fade. They can be wrong. Signals instead: superseded status, referenced file or symbol no longer exists, document older than the code it describes, contradiction candidates flagged between sections on the same entity. These are surfaced in `lint`, never silently down-ranked.

## 8. What it reuses from Undertow

- Neo4j and GDS (community detection, PageRank used only as a build-time centrality hint).
- Gemini embeddings and the batch/backfill approach.
- The graph-theory notes on diversity and bridge nodes.
- Not reused: hooks, Keeper tiers, flash crafting, decay, pursuit and dismissal, Dreamer, Wonder, Gobble, Spider's pruning (BreakWall never prunes; it rebuilds).

Integration option later: Undertow's Prowler-style lookup calls BreakWall `search`, so memory flashes can cite reference docs. Kept as a clean API boundary, not shared storage.

M2 build notes (2026-10-27, by the builder, not decisions by RouterBox):

16. Retrieval unit for indexes is a `Chunk`, not the `Section` node itself. Every section has one or more `Chunk` nodes (`(Section)-[:HAS_CHUNK]->(Chunk)`, deterministic). Sections of at most 1500 chars are one chunk; longer ones are split on blank-line block boundaries (fenced code is never cut mid-fence) into chunks of about 1000 chars or less, each carrying the section heading path. The text, embedding, model name and embed hash live on the Chunk; the full-text and vector indexes are on Chunk. Search results are collapsed back to sections (best chunk per section) and cite the chunk's own line range. Reason: splitting very long sections into extra Section nodes would break the M1 section ids and counts. No text overlap between chunks (the heading path is the shared context); the 'overlap marker' in section 5 is not built.
17. Embed input is heading path + newline + chunk text, capped at 1500 chars. all-MiniLM-L6-v2 truncates at about 256 word pieces (roughly 1000 chars), so text beyond that in a chunk is not seen by the vector side; the 1000-char split target is chosen for that. The embed hash is sha256(model + input); a chunk is re-embedded only when the hash changes, and the count embedded vs reused is logged on every index.
18. Full-text index uses Neo4j's Lucene BM25 with the `english` analyzer (stemming, stop words). Lucene statistics are index-wide, so lexical scores depend on every corpus in the database, not only the one queried. Ranking is reproducible for a fixed database state; adding another corpus can shift lexical scores. Known limitation, not fixed in M2.
19. 'No answer' gating uses raw scores, not the fused score (RRF scores are rank-based and carry no absolute relevance): cosine of the top result for vector and hybrid, BM25 of the top result for lexical. The threshold is picked from the eval set (see eval/results-m2.md) and is provisional.
20. Reproducibility measures found necessary while building M2: (a) vector candidates come from the Neo4j vector index but are re-ranked by exact cosine computed from the stored vectors, with ties broken by chunk id, because the approximate index's own scores reordered near-ties after a rebuild; (b) `indexCorpus` leaves a document untouched when its file hash, commit and chunks are unchanged, and drops and recreates the full-text index whenever anything was written or removed (also on `wipe`), because Lucene keeps deleted documents in its statistics and BM25 scores otherwise depend on index history. Both are covered by tests.
21. Eval outcome (eval/results-m2.md, unreviewed gold, 19 answerable questions): hybrid at default RRF weights is not shown to beat lexical alone (lexical MRR 0.772, hybrid 0.669; hybrid recall@10 84% vs 79%); weight tuning did not survive leave-one-out, so defaults stay 1:1, k=60. The "no answer" gate does not beat always answering in leave-one-out accuracy; it ships as a low-confidence flag only (top-hit cosine below 0.41).

M3 build notes (2026-10-27, by the builder, not decisions by RouterBox). Items 22-26 are written before the code and are the contract it is built to; later items record what building showed.

22. No HTTP service. The CLI and a stdio MCP server share one core (`src/tools.js`) and are enough, so no BreakWall port is chosen or bound (the open "HTTP port" item under "Still to confirm" is closed: none). The MCP server runs as a child process of the client, talks to `breakwall-neo4j` through a read-only driver session (`defaultAccessMode: READ`), and never writes to the corpus or the graph. Tools are prefixed `breakwall_` (search, get, outline, neighbors, work_item, history, lint, status) so they cannot collide with Undertow's `undertow_*`. It is not registered anywhere by the builder; the README carries a paste-ready snippet.
23. `sync` is the real indexing path; `index` stays as an alias. Change detection is by content hash of the whole file. Per sync each file is exactly one of: unchanged (no write at all, no embed), changed (document rewritten in one transaction, only chunks with a new embed hash are embedded), added, renamed, removed (tombstoned) or restored. A sync that finds nothing to do performs zero graph writes (counted from Neo4j's own update counters and reported as `writes`). The cross-document link pass is skipped when no document was written and its digest (links, supersession, work items) is unchanged.
24. Rename rule (kept simple on purpose). A file that vanished and a file that appeared in the same sync are the same document if (1) their file hashes are equal (identical content; among several candidates the same basename wins, then path order), else (2) both have at least 3 headings below level 1 and the Jaccard similarity of their sets of lowercased heading texts (levels 2+) is at least 0.6; best score first, ties by path, one-to-one. Anything else is a delete plus an add. A renamed document keeps its `uid` and gets a `renamed` event (from, to, time) in its history. Node ids stay path-based (`corpus:path#n`), so a rename rewrites the document's nodes under the new path; identity is the `uid`, not the node id. The `uid` is sha256(corpus + first path) shortened; it never changes after that.
25. Tombstones. A document that disappears and matches no rename is kept as a `Document` with `deleted: true`, `deletedAt`, and a `deleted` history event; its `Section` nodes stay (verbatim text, flagged `deleted`) so `history` and `get --include-deleted` can still show what it said; its `Chunk` nodes are deleted. Deviation from the brief: tombstoned text is therefore not searchable, even with a flag. Reason: Lucene statistics are index-wide (item 18), so tombstoned chunks left in the full-text index would shift live BM25 scores and break "ranking is a function of live content" (item 20). Keeping the flag on `get`, `outline`, `neighbors`, `work_item` and `history` covers "visible via history and a flag"; searching dead text is not supported. A file that reappears at the same path un-tombstones the same document (same `uid`, a `restored` event); its chunks are embedded again, because tombstoning drops them. A deleted file that reappears at a different path is a new document (the tombstone stays).
26. What a wipe loses. Files are canonical (principle 1), but tombstones, `uid` continuity after renames, and lifecycle events exist only in the index, since the files cannot say what used to be there. The rebuild check therefore compares the live content graph: tombstoned nodes, `events`, `uid`, `deletedAt` and the link digest are excluded from the dump. A corpus that has never had a rename or deletion rebuilds with the same `uid`s anyway. Back up the volume if the history matters.

27. As built: 22-26 hold. The graph also gets `uid`, `events`, `status`, `workItem`, `phase` on `Document`, `WorkItem` nodes with `BELONGS_TO`, and `SUPERSEDES` edges (one stored direction, newer to older; the plan's `SUPERSEDED_BY` is the traversal of it). Edges declared by a tombstoned document are kept; edges from live documents to tombstones resolve, so `history` keeps its chain. An M2-era index is migrated in place on the first M3 sync (uids minted, one-off writes); the real fixture corpus did exactly that.
28. Cost found while testing: the embed input starts with the heading path, so editing a document's level-1 title changes the path of every section under it and re-embeds all of them (an edit to body text re-embeds one chunk, a rename re-embeds nothing). Left as is; the alternative (embedding without the heading path) was judged worse for retrieval and is an M2 decision. The embedding cache is also per corpus name, so syncing the same files under a new corpus name embeds everything again.
29. Known limits, not fixed: a rename that is both moved and heavily edited, or a file under 3 headings that is moved and edited, is a delete plus an add (the old one is tombstoned, the new one gets a new `uid`). A deleted file that returns under a different path is a new document. Edits are not in `history` (git has them; `provenance.commit` points there). `lint`'s `supersession-target` rule reads the files only, so a legitimate reference to a deleted predecessor is flagged there although `sync` and `history` resolve it through the tombstone.
30. MCP verification is by a hand-written JSON-RPC client over stdio (test/mcp.test.js, scripts/mcp-smoke.js), not by a real Claude Code session, since the server is deliberately not registered. Tool descriptions and the `max_chars` budget have not been tried with an agent.
31. Search results now also carry a `doc` block (uid, status, supersession both ways, work item, phase) and the chunk hash, for the citation provenance. Ranking is unchanged; `annotate` runs after `rank`.

M4 build notes (2026-10-27, by the builder, not decisions by RouterBox). Items 32-38 are written before the code and are the contract it is built to; later items record what building showed.

32. Hard constraint for M4: no LLM and no external API call anywhere in the inferred layer. Deviation from section 4 (entities "extracted by an LLM"): entity extraction is local and deterministic (regex and markdown-aware patterns, frequency/TF-IDF filtering, rule-based canonicalisation with a visible alias table). LLM-based extraction is left as an option pending RouterBox's explicit go, because it would spend money and send the corpus off the machine. Deviation from sections 4 and 8 (communities "with Neo4j GDS"): communities are computed in JS (Louvain, no randomness, fixed tie-breaks). The `breakwall-neo4j` image does ship a GDS jar in its plugins directory (checked read-only), but nothing is installed or configured for it, and a JS implementation is deterministic by construction and needs no plugin; GDS is not used.
33. Layering. Every inferred node and edge carries `layer: 'inferred'`, a `method`, a `run` id and (where it applies) a `score`; nothing inferred is written onto a deterministic node or edge, and no deterministic relationship type is reused. New labels and types: `Entity`, `Community`, `InferredRun` nodes; `SIMILAR_TO` (section-section), `MENTIONS_ENTITY` (section-entity, with `spans` = line/column/surface/method of occurrences), `IN_COMMUNITY` (section-community). The deterministic dump used by `rebuild-check` excludes everything with `layer: 'inferred'`, so the M3 digest of the deterministic layer must not change (it was b692ca1d... for the fixture before M4: 722 nodes, 1022 relationships); the inferred layer gets its own dump and digest, and `rebuild-check --inferred` compares both.
34. Passes (`breakwall infer <dir> [--passes similar,entities,communities]`, also `sync --infer`), each separately switchable and each recomputed whole per corpus, replacing the previous inferred layer in one transaction: (a) `similar`: for each section, top-k (k=3) other sections of other documents by cosine, taken from the chunk vectors already stored (a section's score is the max cosine over its chunk pairs); an edge needs cosine at least a threshold chosen from the data (recorded in item 38); stored once per unordered pair. Zero embedder calls: the pass reads stored vectors and never receives an embedder; the CLI prints the real embedder's call counter. (b) `entities`: patterns = backticked terms, bold terms, file paths, endpoints, ports, ENV_VARS, camelCase/snake_case identifiers, capitalised words and multiword names; kept only if the canonical entity appears in at least 2 sections and in at most 20% of sections (TF-IDF style filtering); canonical key = lowercase, separators (space, hyphen, underscore) collapsed, trailing `()` and a plural `s` removed; the surface forms merged into one entity are stored as its alias table (`entities --aliases` prints it), plus an optional explicit table under `entities.aliases` in the corpus `breakwall.json`. (c) `communities`: Louvain over the live sections with weighted undirected edges: heading-tree CONTAINS 1.0, resolved LINKS_TO 1.0, SIMILAR_TO its cosine (when that pass has run); communities of one section are not materialised.
35. Retrieval signals (flags on `search`/`eval`/MCP `signals`): `similar` = graph-neighbour expansion (neighbours by SIMILAR_TO of the top 3 base hits are added as a ranked list), `entity` = entity-match boost (the query's n-grams are canonicalised and looked up in the entity table; sections mentioning matched entities are ranked by summed idf), `community` = diversification (at most 2 results per community in the top 10, the rest pushed below, order otherwise kept). The first two are fused with the base hybrid section ranking by weighted RRF at a pre-declared weight of 0.5 each, k=60; none of the weights is tuned on the eval set (a sensitivity grid at 0.25/0.5/1 is reported but does not set the default).
36. Decision rule, fixed before the first eval run so that the outcome cannot move it. A pass is on by default only if, against the M2 hybrid baseline (recall@5 74%, recall@10 84%, MRR 0.669, top-1 citation 58%, n=19; one question = 5.3 points): it raises recall@5 or recall@10 by at least one question or raises MRR by at least 0.03, AND it lowers none of recall@5, recall@10, top-1 citation by one question or more, AND it is better on more questions than it is worse (paired on reciprocal rank). A change of less than one question is reported as noise. Everything else ships off by default with the numbers recorded in eval/results-m4.md.
37. `trace` (CLI `trace <from> <to>` and MCP `breakwall_trace`): endpoints are a section (id, or path plus heading), a document path (its title section) or an entity name (alias-aware). The path is the cheapest path (Dijkstra, ties by node id, so it is stable) over the deterministic edges (CONTAINS 1, LINKS_TO 1, NEXT 1.5) and, unless `layers` says otherwise, the inferred ones (MENTIONS_ENTITY 2, SIMILAR_TO 3 minus its score). Each hop shows the edge type, layer, method, score and provenance; when both layers are allowed, the deterministic-only path is returned beside it so the reader can see what is parsed and what is inferred. It runs on the whole corpus graph read into memory (fine at this size).
38. Sync and reproducibility. The inferred layer is recomputed whole per corpus, never patched: `infer` stores a digest of its inputs (section texts, embed hashes, link digest, parameters, alias table) on the `InferredRun` node and does zero graph writes when it is unchanged. A deterministic `sync` that changes documents detaches the inferred edges of the deleted sections but leaves the rest of the layer as it was, so `sync` reports the layer as stale and `status` shows fresh or stale; `sync --infer` refreshes it. The cost of a full recompute is measured and recorded below. Same corpus gives identical edges, entities and communities (test and `rebuild-check --inferred`).

39. As built, similar-to. Threshold 0.70, k=3, chosen before any eval run by looking at the data: of 320 sections, 285 are eligible (body of at least 120 characters; heading-only and stub sections are skipped), and the cosine of each one's best neighbour in another document has deciles 0.54 (10th), 0.69 (50th), 0.83 (90th). Sampled pairs just above 0.50 were unrelated (a Keeper section against a lobby research note, a milestone testing section against a definition of done), around 0.60 mixed, from 0.70 up the pairs were the same subject (a milestone document and its section in the project plan). 0.70 gives 174 edges (about 0.6 per eligible section); 0.60 would give 452, 0.80 gives 26. Same-document pairs are excluded. A section's score is its best chunk-pair cosine, taken from the stored vectors: no embedder is involved.
40. As built, entities. Methods: backtick, bold, file, endpoint, port, envvar, identifier, name. Rules added while building, each from reading the entity list or from a unit test, none from the eval: a capitalised single word at a sentence start only counts if the same entity has a mid-sentence mention elsewhere ("weak mentions"); a capitalised single word that the corpus also uses in lower case prose at least as often is an ordinary word and is dropped (Risk, Type, Graph); a sentence-initial verb glued to a name ("Ask Prowler") loses its first word when that word is an ordinary lower-case word of the corpus; a section-frequency ceiling of max(20% of sections, 3) so tiny corpora keep entities; a key is split on capitals only between a lower-case letter and a capital (so `NEO4J_PASS` is `neo4j pass`). On the fixture: 358 entities, 2045 mention edges, 738 candidates dropped as seen in one section only, 1 as too common, 121 as ordinary words (`breakwall entities` lists them with their alias tables). Each mention edge carries method(s), a tf-idf score, tf, idf and up to 5 spans (line, column, surface, method); each entity carries its alias table. Known weaknesses: generic bold labels and table-header words still slip through (Implementation, Risk, Mitigation); no synonym merging; English-only stop words. The relations DEFINES / USES / DEPENDS_ON of section 4 are not built: they need semantic reading, which is the LLM option of item 32.
41. As built, communities. Louvain over all 320 live sections; edges are heading-tree CONTAINS (weight 1), resolved LINKS_TO (1; a link to a document lands on the document's title section) and SIMILAR_TO (its cosine). Result on the fixture: 19 communities covering all 320 sections (no singletons), modularity 0.782, largest community 51 sections. They largely follow document boundaries because the heading tree is in the graph and the fixture has almost no links; a community label is its three highest-scoring entities. The section 4 idea of PageRank-style centrality as a tie-break hint is not built.
42. Eval outcome (eval/results-m4.md, 19 answerable questions, decision rule of item 36): no signal beats the M2 hybrid baseline, so none is on by default. Baseline reproduced exactly (recall@5 74%, recall@10 84%, MRR 0.669, citation 58%). similar: recall@5 79%, recall@10 84%, MRR 0.456, citation 26% (better on 1 question, worse on 8). entity: recall@5 68%, recall@10 95%, MRR 0.530, citation 37% (3 better, 8 worse). community: recall@5 68%, recall@10 79%, MRR 0.660, citation 58% (0 better, 4 worse). All three together: recall@5 58%, recall@10 79%, MRR 0.393, citation 21%. The only gain larger than one question is entity recall@10 (+2), outweighed by its top-1 loss. They stay shipped as opt-in flags (`--signals`, MCP `signals`). Differences of one question are noise at n=19.
43. Reproducibility and the rebuild check. The inferred layer is a function of the live deterministic graph plus the pass code: the input digest covers section hashes, chunk embed hashes, the heading tree, resolved links, the alias table, the parameters and a hash of the pass source files (so new code never reuses an old layer). Verified: infer twice gives the same output digest; wipe, sync and infer again reproduces run id `beb59a7e40ec` and an identical dump (378 nodes, 2539 relationships); `rebuild-check --inferred` reports both layers identical (test and CLI). The deterministic dump excludes everything with layer inferred; at the same corpus commit the M3 code (commit e7e1e53) and the M4 code give the same deterministic digest (64c3c17d... for the fixture, 722 nodes, 1022 relationships). 48. Hook cold-start measurements (this machine, Windows 11, Node 23, warm OS file cache, five or three runs each, taken before any hook code was written). A bare `node -e 0` costs 195 ms. Importing `neo4j-driver` alone costs about 1050 ms (with `src/graph.js` about 1450 ms), so even a lexical-only hook through the Bolt driver takes 1.6 to 1.8 s wall. Loading the local embedding model in a fresh process costs about 500 ms to import `@xenova/transformers` plus about 445 ms to load and run the first embedding: 1.18 to 1.26 s wall for the model alone, before any Neo4j query; a second embedding in the same process takes 5 ms. A fresh process calling Neo4j's HTTP Query API (`POST /db/neo4j/query/v2`, plain `fetch`, no driver) with one BM25 full-text query takes 250 to 295 ms wall in total (query itself 55 to 90 ms).
49. Hook design decision, from item 48: no warm local process and no vector search in the hook. The hook is a one-shot script that talks to `breakwall-neo4j` over its HTTP Query API with `fetch` and does lexical (BM25) search only. Reasons: (a) the model cold start (about 1.2 s) cannot fit the one-second hard timeout, and the Bolt driver import alone cannot either, so the hook must avoid both; (b) a warm thin-client daemon (model and driver kept loaded) would land at about the same 250 to 300 ms (node start 195 ms plus a localhost call plus 5 ms embed plus the queries; estimated from the measured parts, not built) so latency does not justify it; (c) its only gain would be the hybrid ranking and the cosine gate, and eval/results-m2.md did not show hybrid beating lexical on this set (lexical MRR 0.772, top-1 citation 74%, hybrid 0.669 and 58%); (d) a daemon adds a port, a PID to manage and a second thing that must be started by hand. Consequence and deviation from the M5 brief ("uses the M2 hybrid default", "M2 cosine gate"): the ambient hook ranks lexically and its confidence gate is the lexical one from the M2 eval (top-hit BM25 at least 9.341, applied to every injected hit), because a cosine needs the query embedded. The gate was picked on 24 questions, was in-sample 84% balanced accuracy and passed only 13 of 19 answerable questions: for an ambient injection that is the right direction (silence is cheap, a wrong injection is not), but it is a provisional number calibrated on one corpus (Lucene scores depend on the index-wide statistics, item 18), so it is overridable per project (`minBm25` in the marker file). The inferred signals stay off (item 42). If a warm process is ever wanted, it belongs outside the 3011-3014, 3020-3029, 3030, 7474/7475 and 7687/7688 ports and would be a separate decision.
50. Ambient hook contract. `hooks/user-prompt-submit.js`, one Claude Code UserPromptSubmit hook, not registered anywhere by the builder. Per project opt-in: it does nothing unless `.breakwall.json` exists in the prompt's `cwd` or one of its parent directories (up to 8 levels) and names a `corpus`; the marker may also set `ambient: false`, `limit`, `maxTokens`, `minBm25`, `minChars`. Safety rules of section 6, exactly: a hard one-second wall-clock timer around everything (stdin read, HTTP, formatting) that exits 0 without output; any thrown error, any non-200, a down container, a wrong port, bad credentials, unparseable stdin or a missing `.env` produce exit 0 and an empty stdout, never a non-zero exit (a non-zero hook exit would show errors or block the prompt), and no stderr unless `BREAKWALL_HOOK_DEBUG=1`; prompts under 25 characters or 4 words, slash commands and pure `!` shell lines are skipped; stdout is only the hook JSON `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":...}}` or nothing. The hook never writes to the corpus or the graph (one fixed read-only Cypher statement), and writes only a small per-session habituation file in the OS temp directory (section ids already injected in this session are not injected again).
51. Token cap and the shared budget with Undertow. Injected text is capped at `maxTokens` (default 400, estimated as characters/4 so no tokenizer is loaded; at most 3 hits, each snippet at most 350 characters). Undertow's flashes are at most 2 per prompt in `haiku` mode, so the ambient context a prompt can receive from both together is about 400 (BreakWall) plus the flashes, kept under roughly 700 tokens by convention; the numbers are a documented convention, not a live protocol. Limitation, deviation from section 6 ("skipping anything Undertow already surfaced in the same prompt"): both hooks run for the same event and neither can see the other's output, and doing it would mean reading Undertow's internals, which this milestone must not. What the hook does instead is dedupe against its own earlier injections in the session. An Undertow-side change that would allow real coordination is a proposal (item 55), not built.
52. Staleness (`breakwall stale`, section 7). Report only, read-only, cheap (no embedder, no graph write, one read query, one `git log` over the corpus, files hashed). Four lists: (a) documents whose file changed since the last index (changed, added, removed since last sync) with the sections that differ (by heading path and hash); (b) documents superseded by a newer live document; (c) documents last touched more than N days ago (`--days`, default 90) that a document touched within `--recent-days` (default 14) links to; "touched" is the last git commit time of the file, else its mtime; (d) lint findings that are claims (count-mismatch, dangling-link, supersession-target). Nothing is ranked down, hidden or decayed.
53. Citation format for the Undertow bridge: `bw:<corpus>:<path>#<heading path>@<commit8>` (commit omitted when unknown), e.g. `bw:undertow-fixture:docs/KEEPER.md#The Keeper > Role@bd7f35ff`. It names a section by path and heading and pins a version; it never carries content. `breakwall cite` produces it from a path or section id; `breakwall cite --check "<citation>"` reports ok / changed (the file was committed since) / heading-missing / deleted / unknown. Pure formatting and parsing live in `src/cite.js`.

    - Switch B, vectors on or off per corpus (index time). `vectors` is `true` by default, so vectors stay built and stored for every corpus (items 17-21 unchanged) unless a corpus is switched off. ## 10. Phases

- M0 Fixtures and eval set: collect a representative sample corpus and write 30-50 questions with gold answers (which section answers it). This comes first so every later choice is measured. Questions are mined from RouterBox's real past prompts (rewritten to stand alone) rather than invented, because invented ones are too easy; include a few deliberately unanswerable ones to test "no answer". RouterBox reviews the candidates before they become the eval set.
- M1 Deterministic graph: parser, section chunks, structural edges, link resolution, lint report. No embeddings, no LLM. A ready-made stale-doc test case for the lint: Undertow's `CLAUDE.md` says there are 8 daemons while the charter lists nine (Keeper is the ninth).
- M2 Search: vector search is required from the start (RouterBox's decision, 2026-10-27), not gated on the eval. Build BM25 full-text, embeddings and fusion together, and score all three against the M0 eval set: lexical alone, vector alone, and hybrid. The eval picks the default ranking (hybrid unless it shows otherwise) and tunes the fusion weights; it does not decide whether vectors exist. Undertow's own retrieval eval (2026-09-01, from its memory store, not re-verified here) found hybrid beat either method alone, which is why lexical stays as the other half of the fusion rather than being dropped. `search` / `get` / `outline` through the CLI.
- M3 Incremental sync and tools: hash diffing, rename and tombstone handling, MCP server, `neighbors` / `work_item` / `history`.
- M4 Inferred layer: similar-to edges, entity extraction with canonicalisation, communities, `trace`. Each pass behind a flag and scored against the eval set; keep it only if it beats M2.
- M5 Integration and polish: Undertow bridge, optional ambient mode, staleness checks, docs.

## 11. How we know it works

- Retrieval: recall at 5 and 10 against the gold set, plus citation accuracy (the cited section really contains the answer).
- Reproducibility: same corpus and query give identical ranking across runs.
- Rebuild test: wipe the index, reindex, diff the result.
- Lint health: dangling links and orphans trend down as the corpus is tidied.
- Cost: embeddings spent per reindex stays near zero when nothing changed.

## 12. Risks

- LLM-extracted entities drift and duplicate. Mitigation: they are optional, labelled, and gated by the eval set.
- Chunk boundaries hurt retrieval for long, table-heavy documents. Mitigation: heading-path context on every chunk and block-level handling in M3.
- Over-building. Mitigation: M1 and M2 stand alone as a useful tool; stop there if that is enough.
- Two graphs confusing agents. Mitigation: separate stores and tool names, clear citation format.
